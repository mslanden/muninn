# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- **Run the desktop app (dev):** `npm run tauri dev` — launches Vite on port 1420 (strict) and the Tauri Rust host. `beforeDevCommand` in `src-tauri/tauri.conf.json` starts `npm run dev` automatically.
- **Frontend only:** `npm run dev` (Vite, no Rust host — useful for pure UI work but invoke/`@tauri-apps/*` calls will error).
- **Production build:** `npm run build` then `npm run tauri build` (macOS `.app` bundle).
- **Rust type-check without a full build:** `cargo check --manifest-path src-tauri/Cargo.toml`.
- **Sign a locally-built debug bundle** (adds mic + speech recognition entitlements so voice features work): `npm run sign-dev`. Use after `npm run tauri build --debug`.
- **Launch signed debug bundle:** `npm run start`.
- **On-device transcriber sidecar:** `build.rs` compiles [src-tauri/speech/transcriber.swift](src-tauri/speech/transcriber.swift) with `xcrun swiftc` into `src-tauri/binaries/muninn-transcriber-<triple>` (gitignored); tauri copies it next to the app binary via `bundle.externalBin`. The SpeechAnalyzer code path only compiles against the macOS 26 SDK (`-D HAVE_SPEECHANALYZER`); older SDKs (CI runners) build just the SFSpeechRecognizer fallback. A failed swiftc keeps a previously built binary; a missing one fails the build with instructions.
- **Run Rust unit tests:** `cargo test --manifest-path src-tauri/Cargo.toml --lib` (covers workspace path scoping, dangerous-command detection, `sanitize_tool_pairs`, schema migrations, schedule parsing, the process runner, page-target validation). CI (`.github/workflows/ci.yml`) runs `cargo check`, `cargo test`, and `npm run build` on push/PR. There is no frontend test suite and no linter configured.

## Required env vars / provider config

- `OPENAI_API_KEY` — for OpenAI provider (or save in Settings UI under `llm/openai_api_key`).
- `MINIMAX_API_KEY` (or `ANTHROPIC_API_KEY`) — for the "MiniMax (Anthropic Compatible)" provider. Optional `MINIMAX_ANTHROPIC_BASE_URL` (default `https://api.minimax.io/anthropic`).
- Settings stored in the DB's `app_config` table take precedence over env vars (see `first_non_empty_setting` in [src-tauri/src/db.rs](src-tauri/src/db.rs)).

## Architecture

Muninn is a **single-process Tauri 2 app**: there is no daemon, no sidecar, and no separate backend service. The Rust process owns all state and exposes it to the webview via `#[tauri::command]` handlers registered in [src-tauri/src/lib.rs](src-tauri/src/lib.rs) `invoke_handler!`. The frontend is vanilla JS + Vite (no framework) that calls `invoke(...)` from `@tauri-apps/api/core` and listens to events via `listen(...)`.

### Rust module map (`src-tauri/src/`)

- [lib.rs](src-tauri/src/lib.rs) — `AppState`, app setup, system tray, window event hooks, scheduler + content-watcher spawn, full command registration list.
- [commands/](src-tauri/src/commands/) — every `#[tauri::command]`, split into feature submodules (`chat`, `sessions`, `feed`, `ai_feeds`, `tasks`, `skills`, `connections`, `memory`, `settings`, `gallery`, `workspace`, `terminal`, `projects`, `voice`, `video`, `toolconfig`). All commands are re-exported flat from `commands/mod.rs`, so `lib.rs` registration stays `commands::foo`. This is the only module that should be referenced from JS.
- [db.rs](src-tauri/src/db.rs) — SQLite schema (`init_db` + versioned `run_migrations`), `with_db` accessor, `insert_message`, `add_feed_item`, settings accessors. **DB access goes through an r2d2 connection pool** (8 conns, WAL allows concurrent readers; writers rely on a 5s `busy_timeout`); pragmas run per-connection via the pool's `with_init` (use `execute_batch`, not `execute` — see commit `09fc056`). DB lives at `app_data_dir()/muninn.db` (macOS: `~/Library/Application Support/com.marcelinolanden.muninn/`).
- [llm.rs](src-tauri/src/llm.rs) — the `Provider` enum (OpenAI chat/completions vs Anthropic messages wire formats: auth, request body, SSE parsing, tool-round message shapes) and the single shared `run_tool_loop` used by `chat_with_openai`, `chat_with_minimax_anthropic`, `run_skill_turn` and `run_subagent`. Also `history_to_openai` / `history_to_anthropic` converters, tool-schema JSON (`tool_defs` is the single source for both providers), and the system-prompt builders (`build_system_prompt_with_context` / `build_project_system_prompt`, both of which append `memory::prompt_section` and `skills::prompt_section`). The canonical in-memory history shape is **Anthropic-style content blocks** (`{type:"text"|"tool_use"|"tool_result"}`); OpenAI's `tool_calls` shape is derived on the fly.
- [memory.rs](src-tauri/src/memory.rs) — model-managed long-term memory: markdown notes in `AppState.memory_dir` (`app_data_dir()/memory/<name>.md`, one-line `description:` front matter). The model reads/writes them via the `memory` tool (list/read/write/edit/delete/search, dispatched from `execute_agent_tool`, emits `memory-changed`); every prompt gets the `user/name|about|location` settings, the pinned `about-me` note, and a capped (~4K char) index of the rest. No background extraction or embeddings — the legacy `memory_profile`/`entities`/`relationships`/`episodes`/`embeddings` tables are left in the schema but unused. Note names go through `sanitize_name` (`[a-z0-9_-]`), which is what keeps paths inside the folder — never build a note path from an unsanitized name.
- [skills.rs](src-tauri/src/skills.rs) — skills (these replaced custom agents): `AppState.skills_dir/<name>/SKILL.md` in the standard Agent Skills layout (front matter `name`/`description`/optional `allowed-tools`, markdown body, optional reference files). Every prompt lists skill names + descriptions (~3K char cap); the model loads one via the `skill` tool (list/load/read_file/create/update/delete). **create/update/delete require `ask_user` approval in interactive chat and are refused in background runs** — skills shape future behaviour, so a prompt-injected page must not be able to plant one; the Skills tile's own commands (`save_skill` etc.) are user actions and ungated. `/name` in chat sends `skill` on the `chat` request → `run_skill_turn` (normal project-aware prompt + `active_skill_section`, tools narrowed by `restrict_tools`); tasks pin a skill via the `tasks.skill` column. `read_skill_file` refuses absolute/`..` paths and anything whose canonical path leaves the skill folder. The legacy `agents` table and `tasks.agent_id` are unused.
- [commands/connections.rs](src-tauri/src/commands/connections.rs) — the Connections window's backend. `TOOL_GROUPS` assigns every built-in tool to exactly one connection (Mail, Calendar, Files and shell, Screen and apps, Web, Images, Maps, Video, Built in; anything unlisted shows under "Other tools" — a unit test enforces no tool is in two groups). `get_connections` reports providers (key set/unset only, never values; `in_use` = `llm/provider`), tool groups (status from key + tool switches), and MCP servers (config incl. `"disabled": true` entries + live status). `set_connection_enabled` flips a group's rows in the `tools` table (what `tool_defs` reads) or an MCP entry's `disabled` flag (servers then reload); `check_app_access` runs a trivial Mail/Calendar AppleScript on demand (may show the Automation prompt). When adding a tool, add it to a group here too.
- [tools.rs](src-tauri/src/tools.rs) — workspace-scoped filesystem/search/shell + web-search/fetch + image-gen + Mapbox directions/places. `WorkspaceScope` is the boundary: every fs tool goes through `resolve_within_workspace` and every shell command through `is_dangerous_command`.
- [context.rs](src-tauri/src/context.rs) — context management, sized against `llm/context_budget_tokens` (default 300k tokens, ~4 chars/token, image blocks counted at a fixed 6k chars). In-turn (`maintain`, called by `run_tool_loop` before every request, so tasks/skills/subagents get it too): tool-result images are stripped from all but the newest 2 once 4 have accumulated, and past 80% of the budget old tool-result bodies are cleared down to 55% (head + marker kept, tool pairs untouched, newest 6 never cleared). Cross-turn (`prepare_history`, chat only): past 60% of the budget the older turns are summarized by one non-streaming call to the configured model and stored in `sessions.context_summary` / `summary_upto_id` (schema v11); later turns load only messages after that id, with the summary merged into the first user message. Messages are never deleted and any summarizer failure falls back to dropping the oldest. **Keep the request prefix stable** — provider prompt caches match on it — which is why trimming is batched with hysteresis and why history is not a sliding window. `llm/auto_compact` = `"0"` turns summarizing off.
- [procs.rs](src-tauri/src/procs.rs) — shell processes for the agent. Everything spawns via `/bin/zsh -lc` in its **own process group** with stdout+stderr appended to one temp log file (no pipes, so no reader threads and no pipe-full deadlock); kills signal the whole group (TERM, then KILL) so a dev server's `node` child dies with its wrapper. Foreground: `run_blocking` / `run_async` (timeout, default 300s / max 1800s; the async one also polls the chat's Stop flag) — output is capped head+tail and a non-zero exit is appended as `[exit code N]`. Background: `ProcessRegistry` in `AppState.bg_processes` (max 8 running), started by `run_command` `background: true` (interactive chat only — refused in tasks/subagents so nothing leaks) and managed by the `process` tool (list / output with `wait_for` / stop); stopped when their chat is deleted and on every app exit — tray Quit, `RunEvent::Exit`, and SIGTERM/SIGINT/SIGHUP (a signal handler in `lib.rs` setup; without it `kill` or an installer swapping the app orphaned them). For exits nothing can catch (crash, SIGKILL, power loss) the running set is mirrored to `app_data_dir()/bg-processes.json` and `reap_orphans` stops whatever it lists at the next launch; it kills by stored pid only when the leader's `ps` start time still matches (or the leader is gone but its process group still has members), so a reused pid is never touched. This module does no safety checking — the dangerous-command check stays in the `run_command` arm of `execute_agent_tool`, which must run before `exec_agent_command`.
- [browser.rs](src-tauri/src/browser.rs) — the `capture_page` tool: runs an installed Chromium-based browser (Chrome/Chromium/Brave/Edge, discovered in `/Applications`, not bundled) with `--headless=new`, a throwaway `--user-data-dir`, `--screenshot` + `--dump-dom` + `--enable-logging=stderr`, and returns screenshot (via the `captured_images` side channel) + parsed console lines + page text. Fresh page load per call, no interaction. Allowed targets are decided by `tools::resolve_page_target`: public http(s), **loopback** http(s) (local dev servers), or a workspace file — private-network/metadata hosts and other schemes stay blocked. The e2e test needs python3 + a browser and is `#[ignore]`d: `cargo test --lib browser -- --ignored`.
- [screen.rs](src-tauri/src/screen.rs) — `capture_screen` / `open_app`, plus `load_image_for_model` (what `read_file` uses to show image files to the model: `sips` downscale to 1568px, HEIC/BMP/TIFF→PNG). `capture_screen` with `app` captures that app's window by CoreGraphics window id (`screencapture -l`, id looked up through a JXA `CGWindowListCopyWindowInfo` call) **without focusing it**; `open_app` `background: true` is `open -g`.
- [scheduler.rs](src-tauri/src/scheduler.rs) — `next_run_from_schedule` parses strings like `"every 30s"`, `"daily at 09:00"`, `"every monday at 10:00"`; `run_scheduler` ticks tasks and AI feeds.
- [feeds.rs](src-tauri/src/feeds.rs) — AI feed generation (scheduled LLM jobs that produce feed items with optional images).
- [audio.rs](src-tauri/src/audio.rs) — `cpal`-based recorder; wired to whisper transcription commands.
- [video.rs](src-tauri/src/video.rs) — local ffmpeg engine for the Studio Video tab and the `probe_video`/`analyze_video`/`edit_video`/`generate_shorts`/`compile_videos` agent tools: probe, silence detection, thumbnails, timestamped transcription, and non-destructive `EditPlan` renders (segments/filter presets/text overlays/aspect crop/speed) with `video-render-progress` events and pid-based cancel. Auto-shorts (`run_shorts_pipeline`, exposed as the `video_generate_shorts` command and the `generate_shorts` tool): transcribe → LLM highlight picking (`generate_shorts_specs` in llm.rs, validated/selected by `sanitize_short_specs`) → sequential captioned 9:16 vertical renders into the Content library, emitting a `shorts-progress` stage event plus per-short `video-render-progress` keyed `{job_id}-{n}`; cancel via `video_cancel_shorts`/`request_cancel_shorts` (a `Mutex<HashSet>` flag checked between shorts + SIGKILL of the active sub-render). Segments can be multi-source: a `Segment.source` (default `None` = the main video) points at another video file (b-roll insert) or a still image (silent title/intro card shown for `end-start`s) — `render_edit` probes each distinct source once, adds one `-i` per input, and normalizes inserts (scale-cover/crop/setsar/fps + `anullsrc` for silent audio) so `concat` matches, while caption mapping is cross-source (a `TranscriptMap` keyed by `Segment.source` — `None` = main; each source's words map only into that source's own kept segments via `map_interval_to_output_for_source`, but the cumulative output offset still accumulates over ALL segments regardless of source; `render_edit` takes `&TranscriptMap`, single-video callers wrap via `TranscriptMap::from_single`/`single` for byte-identical behavior); agent `edit_video` sources go through `resolve_within_workspace`, studio paths stay unscoped. Smart reframe (`EditPlan.smart_reframe`, only meaningful when `aspect` narrows the frame) runs the `muninn-framescan` Swift sidecar (Vision `VNDetectFaceRectangles`, compiled by `build.rs` like the transcriber, gitignored, `externalBin`-bundled, located via a `transcriber_helper_path`-style lookup) to detect faces on the MAIN source, then drives a piecewise-constant subject-aware crop-x ffmpeg expression (hysteresis + cut-boundary/insert-centered handling, source→output time mapping) instead of the static center-crop; any scan failure or no-faces result falls back silently to center crop, so a render never fails on reframing. ffmpeg is discovered on disk (Homebrew paths), not bundled; drawtext overlays read from temp `textfile=`s to avoid filter-graph escaping. The e2e render test needs ffmpeg and is `#[ignore]`d: `cargo test --lib video -- --ignored`. Transcription: when the `video/local_transcription` setting is `"1"` (Settings tile → Video, [src/settings.js](src/settings.js)), `transcribe_video` first runs the `muninn-transcriber` Swift sidecar on-device (Apple SpeechAnalyzer on macOS 26 — no network, key, or TCC prompt; else SFSpeechRecognizer with `requiresOnDeviceRecognition`, which does need speech-recognition TCC attributed to the parent app — `npm run sign-dev` covers debug bundles). Any local failure falls back to the cloud whisper `verbose_json` path (Groq `whisper-large-v3-turbo` if a Groq key is set, else OpenAI `whisper-1`). Multi-clip compilation (`run_compile_pipeline`, exposed as the `video_compile` command and the `compile_videos` tool): transcribe + analyze each of 2–10 clips → LLM planning (`generate_compilation_specs` in llm.rs, "takes" retakes-vs-"montage" auto-detect, validated by the pure `sanitize_compilation_spec`) → ONE stitched cross-source render (clip 0 = main input; each clip is a caption source in the `TranscriptMap`) into the Content library, emitting a `compile-progress` stage event + the render's `video-render-progress` keyed by the compile `job_id`; cancel via `video_cancel_compile`/`request_cancel_compile` (shares the generalized `pipeline_cancels` set + SIGKILL used by shorts). The planner emits an explicit clip `source` on every segment; the pipeline rewrites clip-0 segments to `source: None` (the main input). `compile_videos` resolves EVERY path through `resolve_within_workspace`.
- [models.rs](src-tauri/src/models.rs) — shared serde structs + `HistoryMessage` type.

### Chat turn loop (important)

`commands::chat` → `context::prepare_history` loads the session's stored summary plus every message after its compaction point (compacting first if that has outgrown the budget), enforces the hard budget, and calls `sanitize_tool_pairs` so no orphan `tool_use`/`tool_result` survives (providers reject this with a 400) → builds a `Provider` and enters `run_tool_loop` in `llm.rs` → tool rounds run in-Rust via handlers in `tools.rs`, each logged to `tool_logs` and the feed → final assistant message + any hidden intermediate rows persisted. Skill turns (`run_skill_turn`) go through the same `run_tool_loop` (skill instructions appended, `allowed-tools` applied, agent-iteration event). The `subagent` tool runs `run_subagent` in an isolated `<session>::sub-<id>` sub-session (no `sessions` row → nothing persisted to the parent chat), non-interactive, without the `subagent` tool (no nesting), capped at `SUBAGENT_MAX_ROUNDS` via `run_tool_loop`'s `max_rounds`; consecutive `subagent` calls in one model turn run concurrently (`group_parallel_calls` + `join_all`), every other tool stays sequential.

Stop generation: the frontend calls `stop_chat` which inserts the session id into `AppState.stop_requests`; `run_tool_loop` checks this between rounds (chat, skill turns, and subagents, which also peek the parent's flag).

### Safety boundaries (do not weaken)

- **Workspace scoping:** all file tools take a canonicalized `root_canon` and must reject paths that escape it. See `resolve_within_workspace` in [tools.rs](src-tauri/src/tools.rs:117).
- **Dangerous command check:** shell tools run through `is_dangerous_command`. Agent-invoked commands that match are routed through the `ask_user` approval prompt in interactive chat (hard-blocked in scheduled/background runs); only `run_command_scoped_unchecked` skips the check, and it must only be called post-approval. See [tools.rs](src-tauri/src/tools.rs) and `commands::check_command_safety`.
- **Secret settings:** `get_app_settings` redacts any `app_config` key containing `api_key`/`_token`/`_secret` (except the client-side Mapbox token) to the `__secret_set__` placeholder; `set_app_settings` ignores writes of that placeholder. Never add a code path that returns raw secrets to the webview.
- **Agent settings tools:** the LLM's `get_settings`/`set_setting` tools ([config_tools.rs](src-tauri/src/config_tools.rs)) operate only on the declarative `setting_schema()` allowlist — secrets and `mcp/servers` are excluded entirely (never readable or writable by the agent), and gated keys (`safety/*`, `mobile/server_port`) require `ask_user` approval in interactive chat and are hard-blocked in background runs. When adding a new agent-configurable setting, add a `SettingDef` there; never bypass the schema with a raw-key write path.
- **CSP** in [src-tauri/tauri.conf.json](src-tauri/tauri.conf.json) enumerates every allowed `connect-src` origin — adding a new LLM/image/maps provider means editing the CSP.
- **Capabilities** in [src-tauri/capabilities/default.json](src-tauri/capabilities/default.json) are minimal by design. Add new plugin permissions here, not by broadening existing ones.
- **XSS:** the frontend builds DOM via `innerHTML` extensively and relies on `escapeHtml` (see [src/utils.js](src/utils.js)). Any new `innerHTML` sink must escape untrusted data.

### System tray / window behavior

The app runs tray-resident: `WindowEvent::CloseRequested` hides the window instead of closing, and `RunEvent::ExitRequested` prevents exit. Quit is only via the tray menu. `TrayIconBuilder` requires an explicit icon (see commit `85c7e73`) — don't remove the `.icon(...)` call.

### Frontend structure

The frontend is split into ES modules under `src/`:

- [main.js](src/main.js) — entry point: side-effect imports of all feature modules (which registers their tile renderers), sidebar button wiring, and the `bootMain`/`bootPopout` flow.
- [state.js](src/state.js) — shared DOM refs and cross-module mutable state. Reassignable scalars (`loadedSettings`, `mapboxToken`, `cachedSkills`, `focusedTileId`, `nextTileId`) live behind the exported `ui` object because ES module bindings can't be reassigned by importers. `tiles`, `chatStreams`, and `tileMaps` are exported containers (mutated, never reassigned).
- [registry.js](src/registry.js) — the tile-renderer registry. Dependency-free on purpose: feature modules call `registerTileRenderer(type, fn)` at import time, and `tilesys.js` looks renderers up at render time. Putting this anywhere with imports recreates a circular-init (TDZ) crash at boot.
- [tilesys.js](src/tilesys.js) — tile add/remove/focus, grid layout, sidebar, pop-out windows, layout persistence.
- [utils.js](src/utils.js) — pure helpers (`escapeHtml`, `renderMarkdown`, formatters).
- Feature modules, one per tile type: [chat.js](src/chat.js), [feeds.js](src/feeds.js), [web.js](src/web.js), [logs.js](src/logs.js), [tasks.js](src/tasks.js), [toolspanel.js](src/toolspanel.js), [skills.js](src/skills.js), [library.js](src/library.js) (Library tile: Memory/Skills/Content launcher), [memory.js](src/memory.js), [content.js](src/content.js), [workspaces.js](src/workspaces.js), [settings.js](src/settings.js); plus [connections.js](src/connections.js) (Connections window: provider keys + model switching, tool-group switches, MCP add/remove — replaces Settings' old API Keys/MCP/Tools tabs, whose page markup is still in settings.js but no longer reachable), [schedule.js](src/schedule.js) (shared schedule widget), [reader.js](src/reader.js) (article reader windows), [events.js](src/events.js) (all Tauri event listeners), [theme.js](src/theme.js).

Panels are rendered as "tiles" (the `tiles` array in `state.js`) keyed by numeric `id`; `tileMaps` tracks Mapbox instances for cleanup on tile close (tiles can also set a `cleanup()` callback). Theme is handled via `data-theme` on `<html>` and persisted to `localStorage` under `muninn-theme`.

## Conventions / gotchas

- The README still mentions the old `spino` path in one `cd` example — ignore it; the project lives at `Muninn/`.
- When adding a new `#[tauri::command]`, you must (1) define it in the right `commands/` submodule, (2) register it in the `invoke_handler!` macro in `lib.rs`, and (3) call it from the relevant frontend module. Missing step 2 produces a runtime "command not found" error only.
- When adding a new tool the LLM can call, add it to `tool_defs` in [llm.rs](src-tauri/src/llm.rs) (both providers derive their schema from it) and add the dispatch arm in [tools.rs](src-tauri/src/tools.rs) `execute_agent_tool`.
- One-shot (non-streaming) model calls — verdicts, titles, summaries, planning, copy — all go through `llm::complete_once`. Never hand-roll another request/parse block: the helper gives every call at least 4096 output tokens (a reasoning model spends a tight cap thinking and returns nothing visible), retries once with a larger budget when a reply is cut off before any text, strips `<think>` blocks, handles both wire formats, and returns a specific error instead of an empty string. Its `max_tokens` argument is the expected answer size, not a hard cap.
- When adding a new tile type, write `renderXTile(tileObj, body)` in a new module, call `registerTileRenderer("x", renderXTile)` at the bottom, add the side-effect import in `main.js`, and add an entry to `TILE_TYPES` in `tilesys.js` if it should appear in the sidebar.
- Context sizing (`context::value_chars` / `HistoryMessage::char_len`) operates on structured JSON length, not plain text — changes to message shape can silently shift the effective context budget.
- Images on the OpenAI wire format: user attachments go out as `image_url` data-URL parts, and tool images (which can't ride on `tool` messages) follow the round's tool messages in one user message (`Provider::push_round_images`). `send_round` retries once without images if the endpoint refuses them and remembers that per endpoint+model for the process lifetime; it does the same for `stream_options` (sent so OpenAI-format streams report usage and `cached_tokens`).
- The `dist/` folder is committed as the Tauri `frontendDist`; a stale `dist` can cause `npm run tauri dev` to serve old UI if Vite isn't running. Prefer `npm run tauri dev` over running the bundled app during iteration.
